## 1. Справочный коннектор «1С»: сопоставление кодов Т-13 ↔ причины

**Проблема**: коды унифицированной формы Т-13 (Я, Н, РВ, С, К, ОТ, ОД, Б, ДО, У, ПР, НН, НС, В —
Постановление Госкомстата РФ от 05.01.2004 № 1) и коды причин приложения (Я, О, ОД, Д1…Д3, ОГ…
плюс алиасы) — разные справочники. Обмен 3.34 передавал коды как есть: внешняя система получала
«Д1» вместо кода Т-13, а импорт «ОТ» не превращался в «О».

**Решение — единый справочник сопоставления с тремя уровнями:**
1. **Авто-правила** (без настройки): код Т-13 сопоставляется причине, если совпадает с её кодом
   или входит в её алиасы (`ОТ → О`, `ДО → О/ДО`, `Я → Я`…). Логика идентична на клиенте
   (`map1cAuto`) и на сервере (`buildAutoMap`) — по канону `state.reasons`.
2. **Переопределения в каноне** (`state.map1c=[{t13,local,note}]`) — карточка **«Обмен «1С»»**
   (Данные): таблица 14 кодов Т-13 с селектами локальных кодов, источник («авто» /
   «переопределён»), кнопки «⚙ Авто из алиасов», «✔ Валидация», «💾 Сохранить в базе»,
   «⇪ На сервер», «⇩ С сервера», экспорт JSON и CSV. Синхронизируется по ЛВС вместе с каноном.
3. **Общий справочник сервера** — `GET/PUT /api/v1/xchg/map` (файл `PT_MAP_FILE`, права
   staff/admin): действует для всех выгрузок/импортов REST независимо от того, какой клиент
   их выполняет.

**Валидация (клиент и сервер, симметрично):**
- ошибки (блокируют сохранение/выгрузку): неизвестный локальный код (нет в справочнике причин),
  дубль кода Т-13 (регистронезависимо), пустой код, строки без кода;
- предупреждения: непокрытые коды Т-13 (при обмене пройдут как есть), нестандартный код Т-13
  (вне списка формы), несколько кодов Т-13 → один локальный (обратная выгрузка неоднозначна),
  локальные коды вне покрытия.
- Сервер отвечает `{ok,saved,warnings,unmapped,effective}` либо `{ok:0,errors,warnings}` (400);
  каждая попытка PUT попадает в журнал обмена и аудит (`xchg-map`).

**Конвертация в обмене:**
- `GET /api/v1/tabel?y=&m=&map=1c` — локальные коды плана/факта → коды Т-13 (обратный
  справочник: приоритет у точного совпадения кода, иначе первый в каноническом порядке Т-13);
  неконвертированные коды остаются как есть и перечисляются в `warnings:[{code,count,why}]`;
- `POST /api/v1/tabel {map:"1c"}` — входящие коды Т-13 → локальные; неизвестный код проходит
  как есть + warning (ничего не теряется молча);
- CSV-выгрузка конвертируется так же, как JSON (BOM, «;» — без изменений).

## 2. Веб-панель обмена: журнал выгрузок/импортов с повтором

**Серверный журнал** (`PT_XCHG_FILE`, до `PT_XCHG_MAX=300` записей, переживает перезапуск):
каждая операция обмена — `tabel-get` (выгрузка), `tabel-post` (импорт), `skud-post`, `ocr-post`,
`map-put` — пишется с полями: id, время, направление (⇧ выгрузка / ⇩ импорт), статус
(`ok` / `warn` / `error`), подробности, счётчики (строки, применено, неизвестные,
предупреждения, период, события, дни, достоверность OCR), автор, число повторов. Для импортов
сохраняется **исходный запрос** (до 200 КБ) — основа повтора.

**Повтор (ретрай):** `POST /api/v1/xchg/retry {id}` заново выполняет сохранённый запрос —
через те же функции `applyTabelRows` / `applySkudRows`, что и первичный вызов: серверные права
и комплаенс закрытых периодов действуют и при повторе; типичный сценарий «импорт отклонён
из-за закрытого периода → период открыли → ↻ Повтор» отрабатывает без ручной перегенерации
запроса. Права: import (admin/hr). Исходная запись получает `retries+1` и метку времени,
в журнале появляется связанная запись повтора (`retryOf`).

**Три поверхности панели:**
- REST: `GET /api/v1/xchg/log?limit=&kind=&status=` (payload не отдаётся — только флаг
  `hasPayload`), `POST /api/v1/xchg/retry`;
- панель `/admin`: секция **«Обмен «1С» / СКУД — журнал выгрузок и импортов»** на всю ширину —
  фильтры операции и статуса, таблица (время, операция, статус, подробности, счётчики, автор),
  кнопка «↻ повтор» у неудачных записей с payload, состояние справочника Т-13;
- приложение: карточка **«Журнал обмена»** (Данные) — фильтры, статусные пиллы, счётчики,
  «↻ Повтор» с подтверждением, выгрузка видимых строк в CSV; при отсутствии сервера —
  понятная заглушка (проверка по видимости, а не по флагам).

**Живые события:** каждая запись журнала транслируется подключённым клиентам
`{type:"xchg",…}` — карточка обновляется автоматически, ошибки обмена показываются тостом,
предупреждения импортов — тостом «выполнено с предупреждениями».

**Метрики Prometheus:** `wfm_xchg_total{kind,status}`, `wfm_xchg_retries_total`,
`wfm_xchg_journal_entries`, `wfm_xchg_map_items`; `/health` дополнен `xchg` и `xchgMap`;
boot-лог печатает endpoints обмена и файл журнала.

## 3. UX-волна (по списку)

1. **Глобальный drag&drop**: файл можно бросить в любом месте окна (не только в зоне вкладки
   «Импорт») — полноэкранный оверлей «📥 Отпустите файлы — они уйдут в центр импорта»,
   после drop приложение переключается на «Импорт» и ставит файлы в очередь разбора.
2. **Бейджи «ожидают»** на вкладках: «Отпуска» — заявки на согласовании (review),
   «Обмены» — активные заявки смен (new/agreed), «Импорт» — очередь документов
   (в очереди / чтение / ошибка); пересчёт на каждом сохранении и переключении вкладок.
3. **«📋 cURL-примеры»** в карточке администрирования сети: 8 готовых REST-запросов
   (выгрузка табеля CSV/JSON с map=1c, импорт плана, СКУД, чтение и сохранение справочника
   Т-13, журнал, повтор) — с подстановкой текущего токена и адреса сервера, копирование
   в буфер одной кнопкой (clipboard API + fallback).
4. **Живые уведомления обмена** (см. §2) и **журнал с фильтрами и CSV** в клиенте.
5. Справка: блок «Новое в версии 3.35» и новый пункт REST-справки о журнале/ретрае/справочнике.

## 5. Совместимость

- Канон: новое опциональное поле `state.map1c` (массив переопределений) — старые копии читаются
  как раньше, схема API не строже (additionalProperties не ограничены).
- REST: все endpoints 3.30–3.34 без изменений; `map=1c` и новые `/api/v1/xchg/*` — дополнения;
  журнал пишется автоматически, ничего не ломая (ошибка записи журнала не влияет на обмен).
- Сервер: новые файлы `plan-tabel-xchg.json` / `plan-tabel-xchg-map.json` рядом с каноном
  (переопределяются `PT_XCHG_FILE` / `PT_MAP_FILE`); шифрование канона (PT_CANON_KEY) не затрагивается.
- Клиент 3.35 работает с сервером 3.34 (карточка журнала покажет «недоступно», конвертация
  map=1c не сработает до обновления сервера); сервер 3.35 работает с клиентами 3.32–3.34.

## 6. Известные ограничения

- Повтор доступен для импортов табеля и СКУД (сохраняется payload); выгрузки и OCR повторяются
  внешним вызовом (payload изображений не сохраняется — журнал фиксирует результат).
- Обратное сопоставление (локальный код → Т-13) при «несколько Т-13 → один локальный»
  детерминировано (точное совпадение, иначе порядок списка Т-13), но неоднозначность
  подсвечивается предупреждением валидации — рекомендуется 1:1.
- Боевые инсталляции 1С/СКУД заказчика — внешняя сторона обмена; протокол, справочник и журнал
  задокументированы в README-ЛВС.md внутри LAN-пакета.
