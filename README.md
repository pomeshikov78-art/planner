## Развёртывание в локальной сети (без интернета)
1. На одной машине: `npm i ws` рядом с `server/` (или перенесите `node_modules/ws`), затем
   `node server/sync-server.mjs` — сервер напечатает LAN-адреса (`http://192.168.x.x:8787/`).
2. Рабочие места открывают этот адрес: приложение раздаётся с сервера и само подключается к
   синхронизации того же origin'а (реконнект автоматический).
3. Аутентификация (опционально): `node server/make-user.mjs ivanov 1234 editor users.json`,
   затем запуск с `PT_USERS_FILE=users.json` — клиенты входят логином+PIN до обмена данными,
   роль выдаёт сервер. С версии 3.16 пользователей можно вести прямо из `/admin → «Пользователи
   и права»`: добавление, смена роли, сброс PIN, блокировка, отключение модулей (modsOff) и
   точечные права (allow/deny) каждому — применяются у клиентов без перезахода (permsUpdate).
   С версии 3.17 запреты deny применяются и самим сервером: edit — публикация канона, chat —
   мессенджер, sign — самоознакомление, admin — доступ в /admin (отказ пишется в аудит);
   поле emp связывает учётку с сотрудником для вкладки «Мой месяц».
4. Резервный узел: второй сервер с `PT_REPLICA_OF=ws://primary:8787` тянет канон на чтение;
   статус обоих узлов — `GET /status` (автообновление 5 с); авария первичного: на реплике
   `/admin` → «Повысить реплику до primary» (без перезапуска).
5. Эксплуатация: `PT_QUOTA='editor:300'` — квоты публикаций; аудит — `server/plan-tabel-server-audit.jsonl`
   (ротация); панель администратора — `/admin` (состояние, аудит, история и откат канона,
   пользователи и права, журнал сигналов с квитированием — файл `PT_SIG_FILE`); cron-дайджест
   в чат — `PT_DIGEST_CRON='08:30,17:00'` (+ `PT_DIGEST_OUT`, `PT_DIGEST_WEBHOOK` для внутрисетевых получателей).
6. Установка как службы: `sudo bash server/install-service.sh 8787` — systemd-unit с Restart=always
   и enable: сервер сам поднимается после сбоя питания и перезагрузок.
7. Альтернатива без сервера: разложите `…-offline.html` по сетевому диску; обмен — через общую папку
   (кнопка «📁 Подключить папку») или шифрованные копии («🔒 Копия с паролем»).

## Внешний контур (SSO/LDAP, Docker, CI) — проектное решение
Ядро сервера сознано остаётся однофайловым (node + ws) для изолированных ЛВС. Корпоративные
механизмы подключаются внешним слоем без правок ядра:
- **SSO/LDAP/AD**: терминирующий reverse-proxy (nginx/oauth2-proxy/Keycloak) проверяет доменную
  учётку и передаёт логин в защищённом cookie/заголовке; сопоставление логин→роль/emp ведётся в
  users.json (`make-user.mjs` или /admin). Токен сервера WFM выдаёт после `POST /api/v1/login`,
  либо клиент работает с проксированным origin (WS того же origin).
- **Docker/CI**: сервер не требует сборки — образ = node:20-alpine + каталог репозитория;
  `systemd`-unit (`server/install-service.sh`) покрывает bare-metal, Dockerfile тривиален
  (COPY + CMD node server/sync-server.mjs), CI = прогон 8 тестовых наборов из раздела ниже.
- **Прямые коннекторы 1С/СКУД**: обмен файлами уже поддерживается (XLSX/CSV/XML, пресет «1С:ЗУП»,
  план-факт из выгрузок СКУД); REST `/api/v1` (3.30) — точка подключения постоянных интеграций.
